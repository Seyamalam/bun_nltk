# Version-pinned compatibility inventory

This inventory is a compatibility **audit**, not a claim of complete NLTK parity.
It does not replace any working API or the older parity scripts. It intentionally
does not reuse their module-level `True` flags or autogenerated snake_case names
as behavioral evidence.

## Files and reproduction

- `compatibility/inventory.json`: hand-reviewed scope, exclusions, implementation
  routes, source/test anchors, explicit Bun signatures, signature gaps and fixture
  gaps. Change this file when reviewing an implementation.
- `compatibility/discovery.json`: deterministic reflection of installed NLTK
  **3.10.3**, public callable class members/signatures, excluded public attributes,
  every package Bun runtime value export grouped by provenance, source/test SHA256
  hashes and the reviewed mapping/signature baseline. Compact per-module JSON
  avoids thousands of repeated generated lines. Use a JSON viewer for members.
- `scripts/compatibility/discover_nltk.py`: offline Python reflection. Requires
  exactly NLTK 3.10.3; never downloads data or consults the live documentation.
- `scripts/compatibility/inventory.ts`: generate/check, schema validation, real
  source/evidence anchors, drift/regression checks and classification helpers.
- `test/compatibility_inventory.test.ts`: inventory contract tests. These are
  **not NLP behavior or parity tests**.

The recorded environment used Python 3.14.4, Bun 1.4.2, tsrs
`0.18.0-ts7.1.0-dev.20260929`, and Oxlint `1.89.0`. Python standard-library
inherited signatures may change on another interpreter release: use this
environment for byte-identical regeneration, or review the interpreter-specific
diff explicitly. NLTK code was supplied through the parent's pinned oracle path;
this tool does not install or silently substitute a different release.

```sh
bun install --frozen-lockfile
PYTHONPATH=/tmp/opencode/bun-nltk-oracle bun scripts/compatibility/inventory.ts --check
PYTHONPATH=/tmp/opencode/bun-nltk-oracle bun test test/compatibility_inventory.test.ts
npx --no-install tsrs -p compatibility/tsconfig.json --noEmit
npx --no-install oxlint scripts/compatibility test/compatibility_inventory.test.ts
```

After reviewing changes, regenerate using `--write` instead of `--check`, inspect
the JSON diff, then rerun `--check` and the behavioral tests referenced by the
affected mappings. Generation imports Bun entrypoints to discover value exports;
it does **not** invoke NLP operations. Native/WASM artifacts must already be
available for module loading. No binaries are built or fetched by this tool.

Recommended `package.json` entries for the parent (not edited in this milestone):

```json
{
  "compatibility:generate": "bun scripts/compatibility/inventory.ts --write",
  "compatibility:check": "bun scripts/compatibility/inventory.ts --check",
  "compatibility:typecheck": "npx --no-install tsrs -p compatibility/tsconfig.json --noEmit"
}
```

Add `compatibility:check` to the existing **Semaphore** job with the same pinned
NLTK/PYTHONPATH as the differential suite. No GitHub Actions changes are needed.
Full-project tsrs currently has two unrelated unresolved self-package imports in
`examples/js-library/feature-tree.ts`; the dedicated config checks all new
inventory code without hiding those existing full-project errors.

## Contract and counting

At base `405347e`, this selected scope discovers **39 modules, 397 module-qualified
names (338 unique origin-qualified callables), and 917 root Bun value exports**.
There are **42 manually reviewed mappings**, **31 explicit Bun callable signature
bindings**, and **6 mappings with scoped pinned differential evidence**. All
other unique callable targets (296) remain unreviewed gaps, even when a similarly
named export happens to exist. A missing review is not a finding that code is
absent. No whole-NLTK numerator/denominator or percentage is claimed.

`resolveTargets()` gives every selected module target a canonical origin,
classification, signature gaps, missing callable members, missing signature
bindings and fixture status. Imported/reexported NLTK objects reuse canonical
reviews. Family summaries count **module-qualified names**, so reexports can
repeat reviewed mappings; do not sum those rows as unique algorithm coverage.
`resolveBunExports()` lists each entrypoint/name/provenance and reviewed
classification; unreviewed Bun exports are gaps in the audit, not supported APIs
inferred from spelling. Primitive provenance is the entrypoint; object/function
provenance is a deterministic matching reexport module by value identity, not an
automatic claim about its ultimate algorithm implementation.

Categories are `rust-native`, `rust-wasm`, `rust-core`, `ts-algorithm`,
`external-integration`, and `gap`. Rust categories require actual Rust source.
Mixed TS/native paths are described in notes rather than called Rust wholesale.
Throwing external facades are `gap/unsupported`; `external-integration` requires
real integration test evidence. None of the reviewed integrations qualifies yet.

Public-name discovery uses `__all__` where present, otherwise public attributes.
NLTK-owned classes/routines, including bound helpers such as
`wordpunct_tokenize`, are targets. Other public attributes are individually listed
under `excludedAttributes`: constants, modules and third-party imports are not
quietly included in algorithm counts. Public inherited callable class members
are discovered too. Python dunder protocols, type-only Bun declarations and
nested namespace members are explicit exclusions, not measured coverage.

Implementation status, **signature completeness**, and **fixture evidence** are
independent. A Rust algorithm can have scoped differential evidence while missing
constructor/options/members. `implemented-subset` never means a complete class.
All reviewed rows retain explicit gaps. Test evidence distinguishes `wrapper`,
`unit`, `differential`, and `integration`. Only tests asserting NLTK 3.10.3 can
support `pinned-differential`. Tests against project Python reimplementations or
the same bundled payload are not official NLTK behavioral evidence.

## Gate and maintenance

`--check` rejects schema/version mismatch, unknown enums, duplicate mappings,
stale source/test/signature anchors, missing Bun exports or Python members, and
public name/signature/export/source/evidence drift. Python default-object memory
addresses are stripped; host corpus availability and wall clock are not stored.
`--write` cannot silently remove a reviewed mapping/export/member, downgrade an
implemented subset, or discard pinned fixture status. Such an intentional scope
break requires an explicit gate-policy change and review, not a baseline refresh.
This gates inventory regressions, **not** semantic correctness: rerun differential
tests separately. Host data availability never upgrades fixture classification.

To extend a family, add explicit module names and examine all reflected names.
Inspect TS dispatch, Rust core/ABI when relevant, real signatures and the actual
test assertions before adding mappings. Add exact source and test anchors and
write down unsupported options, methods, data, and fixture domains. Add explicit
signature bindings for audited callables; unmapped class members stay gaps.
`--write` plus `--check` makes upstream/public API drift visible in code review.

## Remaining scope

All exclusions are machine-readable in `excludedModules`; `*` explicitly covers
unselected modules/root reexports and unsupported protocols. This milestone does
not complete the 296 unique unreviewed mappings or the 1,710 module-qualified
unmapped class members. It also does not establish complete runtime signatures
for all reviewed classes: the 31 explicit bindings are only the audited subset.
Node/browser artifact exports and nested namespace APIs need separate platform
inventories. The selected-family findings and remaining work are detailed in
`docs/compatibility-family-coverage.md`. Shared exports/build scripts, package
metadata, README and migration docs were left unchanged.
