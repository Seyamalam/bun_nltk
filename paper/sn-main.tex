\title{bun\_nltk: broad NLTK API coverage in TypeScript with Rust/WASM acceleration and local multi-platform builds}

\subtitle{A language-resource toolkit artifact with 241/241 importable names, 432 tests, 91.5\,KiB WASM, and three native targets}

\author*{\fnm{Touhidul Alam} \sur{Seyam}}\email{touhidulalam@bgctub.ac.bd}

\affil[*]{\orgdiv{Department of Computer Science and Engineering}, \orgname{BGC Trust University Bangladesh}, \orgaddress{\city{Chattogram}, \country{Bangladesh}}, \email{touhidulalam@bgctub.ac.bd}. ORCID 0009-0007-7512-1893}

\abstract{The Natural Language Toolkit (NLTK) remains a standard teaching and research library, but it is tied to Python. That excludes npm packages, browser code, edge workers, and offline JavaScript clients that cannot run a Python process.

Existing JavaScript libraries such as natural, winkNLP, and compromise implement parts of NLTK. We built \textbf{bun\_nltk} v0.16.0 to cover more of its API, with selected hot paths in Rust. The package contains native libraries for macOS arm64, Linux x64, and Windows x64, plus a 93{,}712-byte WebAssembly module. All \textbf{241/241 module names} in the NLTK API index import across 46 families. Of these entries, 210 are functional implementations. The remaining 31 comprise 26 shims and five package barrels. The repository records this inventory in an index-derived checklist and a \texttt{COVERED} map in \texttt{scripts/parity-checklist.py}; 432 tests across 66 files check selected behavior.

On \texttt{bench/datasets/gate\_synthetic.txt}, using medians from 2 to 4 rounds, Bun with the native library is $12$ to $20\times$ faster than Python on four measured primitives and $34$ to $253\times$ faster on the measured parser and classifier tasks. A separate 15-round comparison with the TypeScript fallbacks finds median speedups of $1.80\times$ for logistic text training, $1.95\times$ for SVM training, $1.89\times$ for HMM Viterbi decoding, $2.54\times$ for Euclidean K-means, and $2.18\times$ for WordNet loading. Deterministic 95\% percentile-bootstrap intervals remain above $1\times$ for all five operations. The interval for a hot WordNet batch crosses $1\times$, so that result is inconclusive. WASM overhead varies by task: about 5.6\% for n-gram counting in the dashboard and about 65\% for Punkt in the cross-runtime study. Native calls require Bun and a matching prebuilt library. Other hosts use the explicit WASM wrapper. Chromium and Firefox pass the browser harness; Safari, mobile browsers, and edge providers remain untested.}

\keywords{Natural Language Toolkit, WebAssembly, Bun, TypeScript, Rust, NLP toolkit, Language Resources, API coverage, Edge computing}

\section{Introduction}\label{sec:intro}

NLTK \cite{bird2009nltk,loper2002nltk} is a standard reference for natural language processing. Its API spans tokenizers, stemmers, taggers, parsers, language models, WordNet, evaluation metrics, logic, corpora, and other utilities listed at \url{nltk.org/api/nltk.html}. Reproducing that range is difficult. NLTK also requires Python, which rules out direct use in npm packages, browsers, Cloudflare Workers and Vercel Edge, Electron and Tauri applications, and offline JavaScript clients. Researchers must either rewrite a baseline in JavaScript or place Python behind a service.

The main JavaScript NLP packages, \texttt{natural} \cite{natural2024}, \texttt{winkNLP} \cite{winknlp2024}, \texttt{compromise} \cite{compromise2024}, and \texttt{nlp.js} \cite{nlpjs2024}, cover less than $20\%$ of the indexed NLTK modules. They also differ from NLTK on details such as tokenization and stemming. None claims full parity. The API is large, with 241 public modules in 46 families, and it mixes pure algorithms with trained models, GUIs, network clients, corpus downloaders, and external theorem provers.

We chose to port the NLTK interface rather than propose another model. \textbf{bun\_nltk} v0.16.0 is Apache-2.0 software available at \url{https://github.com/Seyamalam/bun_nltk} and on npm as \texttt{bun\_nltk}. Four properties define the release:

\begin{itemize}[leftmargin=1.2em,itemsep=1pt]
  \item Import coverage for 241 of 241 names across 46 families in the NLTK API index snapshot, with 210 functional entries and 31 import-only entries. The latter comprise 26 genuine shims and five package barrels.
  \item 432 tests across 66 files, plus a separate 37-group differential fidelity gate. Selected checks compare Bun output with Python NLTK 3.10.3; shim tests assert the package's documented error contract rather than equivalence to Python failures.
  \item On the recorded benchmarks, representative NLP tasks run 12 to $20\times$ faster than Python, while measured parsers and classifiers reach $253\times$ (see \S\ref{sec:evaluation}).
  \item The npm tarball contains three native targets and a 93{,}712-byte WASM module. Bun loads the matching native library, while hosts without \texttt{dlopen} use an explicit WASM API. Neither path starts Python.
\end{itemize}

We evaluate the package as language-resource software rather than as a new model. The measurements therefore cover API inventory, behavior, runtime, memory, package size, and reproducibility.

\paragraph{Contributions.}
We scraped and enumerated 241 module headings from the NLTK API index and gated import coverage in a local release command. We separated functional implementations from shims, built selected Rust kernels for native and WASM targets, and measured speed, throughput, memory, package size, and cross-platform artifacts. The evaluation reports known output differences instead of treating import coverage as behavioral equivalence.

\section{Background and literature review}\label{sec:related}

\paragraph{NLTK and the Python NLP ecosystem.}
NLTK \cite{bird2009nltk,loper2002nltk} defined the teaching API and still anchors most NLP curricula; we use its indexed module headings \cite{nltk2024} as the oracle for import coverage. Since 2002 the Python ecosystem has grown around it: spaCy \cite{spacy2023} delivers industrial-strength pipelines in Cython for production NER, tagging and parsing; Stanza \cite{stanza2020} provides a multilingual neural pipeline covering 70+ languages on Universal Dependencies; and Hugging Face Transformers \cite{wolf2020transformers} unifies several hundred pretrained Transformer architectures under one API with a shared model hub. These systems push accuracy (\cite{spacy2023,stanza2020,wolf2020transformers}) but are not NLTK-compatible by design; they expose different module structures, data schemas and model-loading conventions, remain Python-bound, and cannot be \texttt{imported} as drop-in replacements for \texttt{nltk.*}.

\paragraph{JavaScript NLP: \texttt{natural}, \texttt{winkNLP}, \texttt{compromise} and \texttt{nlp.js}.}
On npm, \texttt{natural} \cite{natural2024} covers tokenizers, Porter and Snowball stemmers, Bayes and logistic classifiers, TF-IDF, phonetics, and WordNet. \texttt{winkNLP} \cite{winknlp2024} emphasizes fast tokenization, sentence boundaries, and NER, with reported throughput above 650k tokens/s on an M1. \texttt{compromise} \cite{compromise2024} uses a lightweight POS and payload tagger with a roughly 14k-word conjugated lexicon. \texttt{nlp.js} \cite{nlpjs2024} supplies multilingual NLU/NLG, entity management, and chatbot connectors for more than 40 languages. None claims NLTK parity. For example, \texttt{natural} ports Porter and Bayes but omits Punkt \cite{bird2009nltk}, CCG, Glue semantics, tableau provers, and BLEU/GLEU/chrF evaluation \cite{nltk2024}. \texttt{winkNLP} and \texttt{compromise} omit chart parsers, WordNet, and translation metrics. \texttt{bun\_nltk} instead ports the interface, not a model.

\paragraph{Runtimes: Bun, Node, and WebAssembly.}
Bun \cite{bun2024} combines a JavaScript runtime, package manager, test runner, and bundler on JavaScriptCore. Its \texttt{bun:ffi} module loads native libraries with \texttt{dlopen}. WebAssembly \cite{wasm2023} provides portable bytecode and a virtual ISA; Haas et al.\ \cite{haas2017wasm} measured near-native web performance, and the W3C standardized Core Specification v2.0 \cite{wasm2023}. Rust \cite{rust2024} compiles the same kernels to native cdylibs and a \texttt{wasm32-unknown-unknown} module. \texttt{cargo-zigbuild} cross-links the Linux and Windows artifacts locally. Earlier NLP/WASM work usually accelerates an isolated kernel such as a tokenizer. This package also includes classifiers, sequence decoding, clustering, and a packed WordNet loader. Cloudflare Workers and Vercel Edge \cite{cloudflare2024} forbid native code, so they use the WASM API rather than Bun's native bindings.

\paragraph{Language resource evaluation.}
Language-resource software calls for evidence about coverage, reproducibility, measured behavior, and known gaps. Sections~\ref{sec:methodology} and \ref{sec:evaluation} report those properties separately rather than reducing them to one parity claim.

Maintaining import coverage for all 241 indexed names takes a closed loop (Fig.~\ref{fig:pipeline}).

\begin{figure}[!htbp]
  \centering

  \caption{Coverage classification: the inventory distinguishes functional entries from import-only shims. GUI or display-only modules and entries requiring a network or external program become shims with a documented error. Portable algorithms use TypeScript, with Rust/WASM on selected hot paths.   \label{fig:parity-decision}

\paragraph{1. Scrape and enumerate.}
A script fetches \url{https://www.nltk.org/api/nltk.html}, parses its module headings, and emits 241 \texttt{nltk.*} names. We froze the denominator from the 2026-08-24 scrape for this release. Future releases must record a new scrape date and denominator because the live documentation can change. This oracle measures indexed names, not complete API or behavioral equivalence.

\paragraph{2. Checklist and \texttt{COVERED} map.}
\texttt{scripts/parity-checklist.py} diffs the oracle against its \texttt{COVERED} inventory and writes \texttt{docs/PARITY\_CHECKLIST.md} (46 families, 241 entries):
\begin{lstlisting}[float=!htbp,caption={\texttt{scripts/parity-checklist.py} inventory excerpt.}]
COVERED: dict[str, bool] = {
  "tokenize": True,
  "stem.porter": True,
  "app": True,  # import-only package barrel
  # ... 241 entries
}
\end{lstlisting}

\paragraph{3. Classify: real port versus shim (Fig.~\ref{fig:parity-decision}).}
The decision is shown in \texttt{parity\_decision.pdf}. A GUI or display-only entry becomes a shim. The same applies when an operation requires a network service or external program that the package does not supply. Portable algorithms use TypeScript, with Rust for the measured hot paths (token and n-gram counting, PMI collocations, Porter). The inventory contains 210 functional entries and 31 import-only entries. Five import-only entries are package barrels, leaving 26 genuine shim modules. Shims export named symbols and throw \texttt{Error("requires ...; use JS alternative ...")} when unsupported operations are called. Tests assert this specified contract. They do not claim that Python throws the same exception. Fully shimmed groups include \texttt{app}, \texttt{draw}, and \texttt{twitter}; \texttt{chat} mixes re-exports with throwing operations, and \texttt{inference.prover9/mace} requires external binaries.

\paragraph{4. Harness: Bun test versus Python .venv.}
\texttt{bench/} runs selected tasks under Bun and CPython 3.12 with NLTK 3.10.3 on the same data (\texttt{bench/datasets/gate\_synthetic.txt}). Checks cover API existence and sampled outputs, with stated tolerances for floating-point scores and perplexity. Shim tests check the documented \texttt{bun\_nltk} error contract. The suite contains 432 tests across 66 files. A separate differential gate runs 37 behavioral groups against live Python NLTK outputs or versioned NLTK-derived fixtures and writes \texttt{artifacts/fidelity-report.json}. This gate is separate from the import checklist, but the project author still maintains it. Benchmark rounds report median latency.

\paragraph{5. Local release gate.}
\texttt{bun run release:local} performs type checking, linting, 34 Rust tests, 432 TypeScript tests, the 37-group differential fidelity gate, native performance thresholds, binary and package-size limits, tarball-content checks, and a packaged macOS runtime smoke. It builds macOS arm64 directly and cross-builds Linux x64 and Windows x64 with Zig, then builds WASM. Companion wrappers run from a fresh clone on x64 Linux and Windows, compare native Rust with the TypeScript fallback on the same host, install the packed tarball, and write versioned JSON reports. The generated checklist proves name coverage against the frozen documentation index; it does not prove complete functional equivalence. None of these procedures requires GitHub Actions.

\section{Architecture}\label{sec:architecture}

Figure~\ref{fig:architecture} traces the package from TypeScript and Rust sources through native and WASM builds to the supported runtimes.

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.98\textwidth]{figs/architecture.pdf}
  \caption{Architecture: TypeScript APIs call coarse Rust operations for token work, text-model training, HMM decoding, K-means, and WordNet. The local build produces macOS arm64, Linux x64, and Windows x64 libraries plus a 93{,}712-byte WASM module. Bun loads a compatible native library with \texttt{dlopen}; \texttt{WasmNltk.init} explicitly instantiates WASM from bytes or a path.}
  \label{fig:architecture}
\end{figure}

\paragraph{Source: TypeScript plus Rust.}
\texttt{src/} holds the TypeScript implementation (ESM, strict mode), while \texttt{scripts/parity-checklist.py} holds the module-name inventory. \texttt{rust/src/} contains the FFI layer and native kernels. Rust handles ASCII token and n-gram work, PMI windows, Porter, Punkt, full text vectorization plus logistic/SVM optimization, HMM Viterbi decoding, Euclidean K-means, and packed WordNet loading and traversal. The text-training call accepts raw documents and returns one binary model buffer, avoiding a token-by-token FFI boundary. WordNet keeps small JSON requests for compatibility but returns tagged binary buffers rather than JSON objects. Other functional entries use TypeScript, and each migrated operation retains a TypeScript fallback for comparison.

\paragraph{Build: one local command, four binaries.}
\texttt{bun run release:local} drives the release build. \texttt{cargo build} emits the macOS arm64 dylib and WASM; \texttt{cargo zigbuild} emits a Linux x64 shared object with a glibc 2.17 baseline and a Windows x64 DLL. Their sizes are 590{,}080, 728{,}152, 1{,}536{,}512, and 93{,}712 bytes respectively. The package includes all four. Format checks verify Mach-O arm64, ELF x64, PE x64, and WASM signatures before packing.

\paragraph{Runtime selection.}
\begin{lstlisting}[caption={Explicit native and WASM entry points (simplified).},label={lst:binding}]
import { countTokensAscii, WasmNltk } from "bun_nltk";

const nativeCount = countTokensAscii(text); // Bun dlopen
const wasm = await WasmNltk.init({ wasmBytes });
const portableCount = wasm.countTokensAscii(text);
wasm.dispose();
\end{lstlisting}
The root API imports Bun's native bindings, so native calls require Bun and a matching library. \texttt{WasmNltk} is a separate explicit API and accepts caller-supplied bytes for non-filesystem hosts. For the dashboard's n-gram task, the native median is 0.0741\,s and the WASM median is 0.0798\,s, so WASM is about 5.6\% slower. That result does not generalize to every task: in the M5 Pro study, Punkt takes 1.2\,ms native and 2.0\,ms in WASM.

\paragraph{Distribution: npm.}
\texttt{package.json} ships \texttt{index.ts}, \texttt{src/}, \texttt{corpora/}, selected compact models, three native binaries, and WASM. It excludes Rust sources, build scripts, and the 30\,MB full WordNet pack. The validated tarball contains 213 files, is 1.72\,MB compressed and 4.53\,MB unpacked, and has no install-time lifecycle scripts. The local smoke test installs that tarball in a clean project and executes the packaged macOS binary. The release commit also contains the three prebuilts and WASM so a Linux or Windows tester can clone the repository and run one wrapper without a compiler toolchain. Each wrapper packs and installs the tarball on the native operating system before running same-machine native-versus-TypeScript comparisons. Cross-built or emulated runs are not used for cross-platform performance claims.

\section{Evaluation}\label{sec:evaluation}

\paragraph{Setup.}
Table~\ref{tab:speedup} uses a recorded single-core Linux x64 runner with CPython 3.12, NLTK 3.10.3, and Bun with the native library. The seeded \texttt{bench/datasets/gate\_synthetic.txt} file is 7{,}941{,}847 bytes, contains 1{,}148{,}706 tokens and a 156{,}675-item vocabulary, and includes about 2.92\% non-ASCII text from URLs, handles, and emoji. We ran 2 to 4 rounds per task and report medians without dispersion estimates or confidence intervals. Absolute medians are committed in \texttt{artifacts/bench-dashboard.json}; for example, collocations take 1.2999\,s in Python and 0.1033\,s natively, while Porter takes 3.3024\,s and 0.2617\,s. Tables~\ref{tab:crosstime} and \ref{tab:realcorpora} are separate experiments on a MacBook Pro M5 Pro arm64 with NLTK 3.10.3, two warmups, and five measured rounds. Table~\ref{tab:nativemigration} uses that same Mac for 15-round native-versus-TypeScript comparisons. Its 95\% intervals use 10{,}000 deterministic percentile-bootstrap resamples of the median speedup ratio. We do not pool results across these environments.

\paragraph{Native migration benchmark.}

Native word tokenization, Punkt, and Porter take less time than their Python rows. WASM overhead varies: word tokenization is close to native, while Punkt rises from 1.2 to 2.0\,ms. The 0.7\,ms WASM counting cells do less work than the Python and native PMI path, so they cannot support a $212\times$ end-to-end claim. Native is slower than Python on collocation scoring and FreqDist because the wrapper materializes candidate pairs and JavaScript objects. These timings measure the implementations, not algorithmic equivalence.

\paragraph{Scaling with input size and real corpora.}

\paragraph{Throughput and resources.}
On the token path we see about 15.5\,M tokens per second and 0.67\,M sentences per second. The tagger does roughly 1.20\,M tagged tokens per second. Peak RSS delta is about 908\,MB (corpus loaded) with roughly 187\,MB heap. That is the dataset and the dictionary talking, not the 91.5\,KiB WASM payload.

\paragraph{Correctness checks and known gaps.}
The dashboard records sampled comparison flags, but these are not proofs of full equivalence. Its Punkt and sentence-count checks are false because Python and TypeScript segment the synthetic text differently. We treat this as a fidelity gap, not measurement noise. The 432-test suite checks selected contracts and examples. The separate 37-group differential gate checks live NLTK outputs or versioned NLTK-derived fixtures, while \texttt{PARITY\_CHECKLIST.md} checks import names only. None establishes complete behavioral equivalence across all inputs.

\section{Case studies: end-to-end pipelines}\label{sec:usecases}

Benchmarks isolate kernels, while applications chain them. Four scripts under \texttt{paper/usecases/} exercise complete pipelines. They print the outputs reproduced below from deterministic runs of the release build.

\subsection{Sentiment classification over movie reviews}\label{sec:uc-sentiment}

The sentiment pipeline follows the classic NLTK tutorial: load 1{,}000 labeled movie reviews, extract the top 2{,}000 word-presence features, train a Naive Bayes classifier, and evaluate on 200 held-out documents. The corpus has 500 positive and 500 negative reviews. A Fisher-Yates shuffle uses a Mulberry32 generator with seed 1337 before the 80/20 split. The seeded \emph{bun\_nltk} run reaches 78.5\,\% holdout accuracy in about 240\,ms. The corresponding Python NLTK baseline scores 72.1\,\% with its seeded random split and 80.5\,\% with a label-sorted split. The package result lies inside that split-sensitive range and does not establish an accuracy improvement.

\section{Discussion}\label{sec:discussion}

\paragraph{Distribution through npm and WASM.}

The npm registry contains about two million packages and is the default distribution channel for JavaScript. \texttt{npm install bun\_nltk} installs the TypeScript sources, compact models, native prebuilts, and WASM without invoking a compiler or Python.

The explicit \texttt{WasmNltk} API supports hosts that forbid \texttt{dlopen} \cite{cloudflare2024}. The committed browser tests pass in Chromium and Firefox. We have not recorded results for Safari, mobile browsers, or edge providers, so compatibility with those hosts remains unverified.

\paragraph{Known limits.}

The inventory contains 31 import-only entries: five package barrels and 26 shim modules. The \texttt{app}, \texttt{draw}, and \texttt{twitter} groups consist entirely of shims. \texttt{chat} mixes working re-exports with unsupported operations, and \texttt{inference.prover9/mace} requires external binaries. Unsupported calls throw \texttt{Error("... requires ...; use JS alternative ...")} and name an alternative when one exists. Tests check that package-specific contract. Importability does not imply Python-equivalent behavior.

Rebuilding all four binaries on Apple Silicon requires Rust, the \texttt{wasm32-unknown-unknown} target, Zig, and \texttt{cargo-zigbuild} \cite{rust2024}. Package users receive prebuilts and do not compile Rust during installation.

The optional full WordNet dictionary is 30{,}602{,}237 bytes, about 30\,MB, while the WASM binary is 93{,}712 bytes. The npm package ships mini and extended WordNet JSON files but excludes the full pack. The memory peak in Table~\ref{tab:speedup} includes the loaded data as well as executable code.

\paragraph{When to use bun\_nltk.}
The package is suitable when its documented functional subset and measured fidelity fit the task. Code that depends on exact Punkt segmentation, NLTK's statistical named-entity labels, Tk GUIs, Twitter access, or bundled \texttt{prover9}/\texttt{mace} behavior needs separate validation or another implementation.

%--------------------------------------------------------------------
\section{Separate roles of WASM and npm}\label{sec:unlocks}

\subsection{WASM as an execution target}

WASM runs in browser tabs, WebWorkers, ServiceWorkers, and edge runtimes that forbid native code \cite{wasm2023,cloudflare2024}. The 91.5\,KiB module supports client-side and offline tools without a Python process. Download and startup time depend on the network, host, cache, and surrounding JavaScript, and this study does not measure deployment latency. Chromium and Firefox pass the browser tests. Safari, mobile browsers, and edge providers remain untested.

\subsection{npm as a distribution channel}

The npm tarball contains ESM imports, focused subpath exports, selected models, and native/WASM artifacts under one version. \texttt{docs/API.md} documents the API. The release command runs 432 tests and the 37-group differential gate locally, without a hosted CI account.

WASM supplies the execution target; npm supplies the package. Neither removes the need to test each host.

\section{Threats to validity}\label{sec:threats}

\paragraph{Construct validity.}
The 241-entry denominator comes from module headings scraped from the NLTK API documentation on 2026-08-24. It measures import-name coverage, not every symbol or behavior, and the denominator may change with the documentation. We therefore report 210 functional entries separately from 31 import-only entries. Five of the latter are barrels and 26 are genuine shims. The author wrote both the implementation and the differential gate, which creates a circularity risk even though Python generates many expected outputs at run time. External test suites and downstream replications are still needed.

\paragraph{Internal validity.}
Table~\ref{tab:speedup} comes from a recorded single-core Linux x64 environment and reports medians of 2 to 4 rounds without variance or confidence intervals. Tables~\ref{tab:crosstime} and \ref{tab:realcorpora}, plus Fig.~\ref{fig:scaling}, come from one MacBook Pro M5 Pro arm64 with five measured rounds and two warmups. Table~\ref{tab:nativemigration} uses 15 rounds per implementation on the same Mac and reports deterministic 95\% percentile-bootstrap intervals. Fifteen samples still give limited tail information, and sequential native/TypeScript runs may retain order effects. We keep the Linux and Mac environments separate. Some cross-runtime cells perform reduced work: Node uses morphy on 20k words rather than Porter on 100k, and two WASM cells count without completing the Python/native scoring pipeline. Timer granularity also limits the 0.01\,ms everygrams row. The reported local versions are Bun 1.4.0, Node 24.19.0, CPython 3.12.13, and NLTK 3.10.3.

\paragraph{External validity.}
The browser harness exercises Chromium and Firefox, but no browser result JSON is committed. Safari, mobile browsers, and edge providers remain untested. The npm release includes native binaries for macOS arm64, Linux x64, and Windows x64. The packaged macOS binary has run on the author's machine. Clone-and-run validators are provided for native x64 Linux and Windows hosts, but their external reports remain outstanding at the time of writing. We do not substitute Wine, cross-compilation, or an emulated architecture for those results. The English synthetic data and selected corpora do not represent every language, domain, input encoding, or deployment host.

\paragraph{Conclusion validity.}
Runtime speed and behavioral fidelity are separate claims. Similar scaling slopes do not establish algorithmic equivalence, and import coverage does not establish functional coverage. Punkt segmentation differs on the dashboard sample, and the rule-based named-entity example disagrees with Python NLTK on Microsoft, Apple, and OpenAI. The benchmark comparisons support only the workloads, implementations, and environments described here.

%--------------------------------------------------------------------
\section{Conclusion}\label{sec:conclusion}

We built a TypeScript NLP toolkit with import coverage for all 241 names in a frozen NLTK documentation index. The inventory contains 210 functional entries, 26 genuine shims, and five import-only package barrels. A 432-test suite and a separate 37-group differential gate check selected contracts, while the paper records known Punkt and named-entity fidelity gaps. On the recorded Linux benchmark, selected native tasks range from $12\times$ to $253\times$ faster than Python. The newer 15-round M5 Pro comparison measures $1.80\times$ to $2.54\times$ median speedups for native text training, HMM decoding, K-means, and WordNet loading. Their 95\% intervals remain above $1\times$. The WordNet hot-batch interval crosses $1\times$, so that result is inconclusive.

GUI, network, and external-binary operations remain shims. The optional full WordNet payload is about 30\,MB, and rebuilding all targets needs Rust and Zig. Browser validation does not yet cover Safari, mobile, or edge hosts. Native Linux and Windows package reports still need to be collected from those operating systems.

The immediate release task is to collect and archive the native Linux and Windows reports. External fidelity tests, Safari and edge-host runs, a versioned model registry, and a public API-index diff remain open work.

Code: \url{https://github.com/Seyamalam/bun_nltk} (v0.16.0, Apache-2.0). Package: \url{https://www.npmjs.com/package/bun_nltk}. WASM: \texttt{native/bun\_nltk.wasm} (93{,}712 bytes). Raw benchmark JSON and deterministic data-generation seeds are committed under \texttt{artifacts/}, \texttt{paper/bench/}, and \texttt{bench/generate\_synthetic.py}. \texttt{paper/bench/native\_migration\_results.json} records the 15-round timings, raw samples, and bootstrap intervals. \texttt{artifacts/fidelity-report.json} records the 37 behavioral groups and versions. \texttt{bun run release:local} reproduces the author's local package validation.
